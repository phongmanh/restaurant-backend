## 1. Scope
**In:**
- The rules every endpoint follows: route groups, JSON conventions, headers, pagination (§2).
- The error model and the error-code catalogue (§3).
- Idempotency (§4) and optimistic locking (§5).
- The `Caller`: who is calling, and how a request becomes one (§6). How a transaction is bound to one restaurant (§7).
- Staff and admin sign-in, MFA, refresh, sign-out, invitations, password resets and password change (§8). These are the `/v1/auth/*` routes.
- The audit log (§12) and the rate-limit port (§11).

**Out (in other feature designs):**
- **Issuing** invitations and resets, changing roles, deactivating staff and resetting an admin's TOTP: `restaurants` (FR-040, FR-041). That design calls the account operations defined here.
- Guest table-session tokens: `tables` (ADR-0006). This design only defines `Caller.Guest`.
- What a suspended restaurant may still do: `restaurants` (FR-043). Sign-in here only calls the check.

## 2. Conventions for every endpoint
**Route groups.** The path prefix picks the authentication, so a route can't end up in the wrong group by accident. It also lets the WAF set rules per prefix.

| Prefix | Who | Authentication |
|---|---|---|
| `/v1/auth/*` | Anyone | None, except: a refresh cookie on refresh and sign-out; a staff or admin access token on `GET /v1/auth/me` and `POST /v1/auth/password` (§10) |
| `/v1/guest/*` | Guest device | Table-session token (ADR-0006, `tables` design) |
| `/v1/staff/*` | Manager, waiter, kitchen | Staff access token, `aud` = `staff` |
| `/v1/admin/*` | Platform admin | Admin access token, `aud` = `admin`, `amr` contains `otp`, and `is_platform_admin` in the database |
| `/internal/jobs/*` | Vercel Cron | `Authorization: Bearer <CRON_SECRET>`, compared in constant time; not in the contract |
| `/health` | Platform | None. Returns 200 without touching the database |

Staff paths carry no restaurant ID: the restaurant always comes from the caller (§6). Admin paths name the restaurant explicitly, e.g. `/v1/admin/restaurants/{restaurantId}`.

**JSON.**
- Field names are `snake_case`. Unknown fields in a request are ignored, so newer clients keep working against older servers; clients ignore unknown fields in responses (NFR-COMPAT-01).
- Absent optional fields are left out of responses, not sent as `null`.
- IDs are UUID v7 strings.
- Times are RFC 3339 in UTC with `Z` and millisecond precision, e.g. `2026-10-15T09:30:00.123Z`.
- Money is `{"amount": "125000", "currency": "VND"}`: the amount is a string of whole đồng, so no client rounds it through a float.
- Requests are `Content-Type: application/json`, at most 64 KB (larger → `413 payload_too_large`). The one exception is the menu image upload: a raw image body of up to 4 MB (menu §6, CR-004).

**Lists.** Cursor pagination: `?limit=` (default 50, at most 200) and `?cursor=`. The response is `{"items": [...], "next_cursor": "..."}`, and `next_cursor` is absent on the last page. The cursor is opaque base64url (the sort key of the last item); a bad cursor → `400 validation_failed`.

**Headers.**

| Header | Direction | Rule |
|---|---|---|
| `X-Request-ID` | Response, always | Generated by the service (UUID v7). Also in the MDC, the trace and every problem body as `request_id`. A client-sent value is logged as `client_request_id` but never trusted as ours |
| `X-Client` | Request, optional | `<app>/<semver>`, e.g. `customer-android/1.0.0`. Recorded in metrics (architecture §5). Below the configured minimum for that app → `426 client_upgrade_required`. Absent → allowed |
| `Idempotency-Key` | Request | §4 |
| `ETag`, `If-Match` | Both | §5 |
| `Retry-After` | Response | On every 429 and 503, in seconds |
| `Cache-Control: no-store` | Response | On every `/v1/guest`, `/v1/staff`, `/v1/admin` and `/v1/auth` response, except the guest and staff menu reads, which send `private, no-cache` with an `ETag` (menu §2, CR-004) |

**CORS.** An allow-list of the web apps' origins, from config. Allowed request headers: `Authorization`, `Content-Type`, `Idempotency-Key`, `If-Match`, `X-Client`. Exposed response headers: `ETag`, `Location`, `Retry-After`, `X-Request-ID`, `Idempotent-Replayed`. Credentials are never allowed cross-origin: the staff and admin web apps call the API through a same-origin rewrite (§8.3), so CORS only serves the customer web app, which sends a bearer token and no cookies.

## 3. Error model
Every error is RFC 9457 problem details, `Content-Type: application/problem+json`:

```json
{
  "type": "/problems/validation_failed",
  "title": "Request validation failed",
  "status": 400,
  "code": "validation_failed",
  "request_id": "01929c3e-...",
  "errors": [
    { "field": "/lines/0/quantity", "code": "out_of_range", "message": "must be between 1 and 20" }
  ]
}
```

- `code` is the stable, machine-readable field. Clients switch on it and show their own localised text (architecture §11 i18n). `title` and `detail` are English, for developers only, and never contain personal data or internals.
- `errors` appears only on `validation_failed`. `field` is a JSON Pointer into the request body, or `query.<name>` / `header.<name>`.
- In code, services return or throw a sealed `DomainError`. One StatusPages mapping turns it into the response. Any other exception → `500 internal_error`: the stack trace goes to the log, never to the client.

**Status rules.**
- The order of checks is: 401 (who are you) → 403 (may your role do this at all) → 400 (is the input valid) → 404 (does it exist in your restaurant) → 409/412 (state).
  - The role check doesn't look at the object, so a 403 can't reveal that another restaurant's object exists.
- An ID of another restaurant or another table session is `404 not_found`, the same as an ID that doesn't exist (FR-042).
- A business rule that the current state blocks is a 409 with its own code (e.g. `order_not_cancellable`). The feature designs add those codes.

**Catalogue: shared codes** (feature designs add their own; the full list lives in the contract under `x-error-catalogue`).

| Status | `code` | When |
|---|---|---|
| 400 | `malformed_request` | Body isn't valid JSON, or a field has the wrong type |
| 400 | `validation_failed` | Field rules failed; see `errors` |
| 400 | `idempotency_key_required` | §4: the operation needs an `Idempotency-Key` |
| 400 | `password_rejected` | §8.6: too short, too long, or on the common-password list; `errors[0].code` says which |
| 401 | `unauthenticated` | Token missing, malformed, forged, expired, wrong audience, or its session has ended. Comes with `WWW-Authenticate: Bearer` |
| 401 | `invalid_credentials` | Sign-in, MFA step or password change: wrong email, password or code, a locked account or a deactivated account. Always the same body |
| 403 | `forbidden` | The caller's role lacks the operation (authorisation matrix) |
| 403 | `restaurant_suspended` | The caller's restaurant is suspended (FR-043; scope in the `restaurants` design) |
| 404 | `not_found` | Doesn't exist, or belongs to another restaurant or session |
| 404 | `link_invalid` | An invitation or reset link that is unknown, used, replaced or expired; one code for all, so a link can't be probed |
| 409 | `idempotency_request_in_progress` | §4: the same key is still being processed |
| 412 | `precondition_failed` | §5: `If-Match` is stale |
| 413 | `payload_too_large` | Body over 64 KB |
| 415 | `unsupported_media_type` | Body isn't `application/json` |
| 422 | `idempotency_key_reused` | §4: the same key with a different request |
| 426 | `client_upgrade_required` | Mobile app below the minimum version |
| 428 | `precondition_required` | §5: `If-Match` missing on a versioned resource |
| 429 | `rate_limited` | §11; `Retry-After` set |
| 500 | `internal_error` | Unexpected error; `request_id` lets support find it |
| 503 | `service_unavailable` | Database unreachable or timed out (architecture §10); `Retry-After` set |
| 503 | `service_busy` | §8.1: no Argon2id slot free within 2 s; `Retry-After: 1` |

## 4. Idempotency
**In plain words:** a phone on a bad network sends "place order", the answer gets lost, and the app sends it again. The `Idempotency-Key` header is a random ID the app picks once per user action and repeats on each retry. The service remembers the key with its answer, so the second request gets the first answer back instead of creating a second order.

- **Where it's required** (architecture §10, CR-005): order placement (guest and staff), session close and restaurant onboarding. Operations that a database constraint already makes safe to retry (session open/join, waiter calls) take no key. The feature designs mark these operations in the contract. Missing key → `400 idempotency_key_required`. Other `POST`s ignore the header.
- **Format:** 1–64 characters of `[A-Za-z0-9_-]`; a UUID is recommended.
- **Scope:** the key is unique per caller and operation: `(scope, operation, key)`, where scope is `guest:<device id>`, `staff:<id>` or `admin:<id>`, and operation is the route template, e.g. `POST /v1/guest/orders`. Two devices can't collide, and one device can't replay another's answer.
- **Request fingerprint:** SHA-256 over the operation, the path parameters and the raw body bytes. The same key with a different fingerprint → `422 idempotency_key_reused`.

**How it works, inside the operation's own transaction** (so the key and the change commit or roll back together):
1. `INSERT INTO idempotency_keys (...) ON CONFLICT DO NOTHING`.
2. If the row was inserted, this is the first request: do the work, `UPDATE` the row with the response status, the headers worth replaying (`Location`, `ETag`) and the body, then commit.
3. If it wasn't inserted, a row with that key exists. Read it:
   - different fingerprint → 422;
   - otherwise replay the stored response with `Idempotent-Replayed: true`.
4. **Two copies at the same moment.** PostgreSQL makes the second `INSERT` wait until the first transaction commits or rolls back. Then the second request either replays the answer, or (if the first rolled back) does the work itself. `lock_timeout` 2 s on that statement; past it → `409 idempotency_request_in_progress`, and the client retries.

Only successful (2xx) responses are stored. A rejection rolls back the whole transaction, key included, so a retry is checked again against the current state: if the sold-out item is back, the retry succeeds. That's the intended behaviour.

**One-time secrets are never stored.** Some responses carry a secret that may be shown only once, such as an invitation link. Their stored copy leaves the secret out, and a replay **issues a fresh one** that replaces the earlier one. The client never saw the first answer, so nothing usable is lost, and no secret sits in `idempotency_keys` for 24 h. The first user is onboarding (restaurants §5).

Keys are kept 24 h; the hourly purge job deletes older ones (architecture §10).

## 5. Optimistic locking
**In plain words:** two managers open the same menu item and both press save. Without a check, the second save silently overwrites the first. Each versioned row has a `version` number. A read returns it as the `ETag`, an update has to send it back in `If-Match`, and if someone saved in between, the numbers no longer match and the update is refused.

- Versioned resources (architecture §10): orders, menu items, tables, table sessions, restaurant profile; staff accounts too (§9).
- A read of one versioned resource returns `ETag: "<version>"` (a strong ETag).
- `PATCH`, `PUT` and `DELETE` on one need `If-Match: "<version>"`. Missing → `428 precondition_required`. Stale → `412 precondition_failed`, and the client reloads.
- The update is `UPDATE ... SET ..., version = version + 1 WHERE id = ? AND restaurant_id = ? AND version = ?`. 0 rows → read again: not there → 404, there → 412.
- State changes through action endpoints (e.g. `POST /v1/staff/orders/{id}/status`) take `If-Match` too. The `orders` design decides which.

## 6. The caller
`Caller` is what every service method receives. It's built from the token and the database, never from the request body.

```kotlin
enum class StaffRole { MANAGER, WAITER, KITCHEN }

sealed interface Caller {
    data class Guest(val deviceId: DeviceId, val sessionId: TableSessionId,
                     val tableId: TableId, val restaurantId: RestaurantId) : Caller
    data class Staff(val staffId: StaffId, val restaurantId: RestaurantId,
                     val role: StaffRole, val sessionId: StaffSessionId) : Caller
    data class Admin(val staffId: StaffId, val sessionId: StaffSessionId) : Caller
}
```

**Staff and admin requests**, in a Ktor authentication provider per route group:
1. Verify the access token (architecture §7): ES256 only, signature against the staff key set by `kid`, `iss`, `aud`, `exp` with 30 s leeway. Admin group: `amr` contains `otp`. Any failure → 401, with one exception: a token that verifies but has `aud` = `staff` on `/v1/admin/*` → `404 not_found`, so the admin routes look absent to restaurant staff (FR-040; owner, 2026-10-15, restaurants §15 Q1).
2. One query, outside the tenant's transaction (the tables in §9 are global):
   ```sql
   SELECT a.restaurant_id, a.role, a.is_platform_admin, r.status AS restaurant_status
   FROM staff_accounts a
   JOIN staff_sessions s ON s.staff_id = a.id
   LEFT JOIN restaurants r ON r.id = a.restaurant_id      -- NULL for platform admins
   WHERE a.id = :sub AND s.id = :sid
     AND a.status = 'active' AND s.revoked_at IS NULL AND s.expires_at > now()
   ```
   No row → 401. Staff group with `is_platform_admin` true, or admin group with it false → 401.
3. The same query also joins `restaurants` (a global table, restaurants §2; owner, 2026-10-15) to read the restaurant's `status`. If the restaurant is suspended and the endpoint's registry entry doesn't have `allowedWhenSuspended` → `403 restaurant_suspended` (FR-043, restaurants §6).

Because step 2 joins the session, **sign-out, a password change, a role change and deactivation take effect on the very next call**, not up to 15 min later. That's stronger than FR-010 asks for ("at the latest when the access token expires"), at the cost of one indexed lookup per call.

**Role checks** are in the services, not the routes, so a second route to the same operation can't skip them. A helper `caller.requireRole(MANAGER)` throws `DomainError.Forbidden`. Each feature design maps the authorisation matrix (architecture §7) to its endpoints, and the matrix test covers every endpoint × caller (test-plan §2).

## 7. Tenant transactions
From ADR-0005, as verified in S-2:
- `Transactor.inTransaction(restaurantId) { ... }` opens a transaction and first runs `SELECT set_config('app.restaurant_id', ?, true)`. Forced RLS then returns only that restaurant's rows, and a missing setting returns 0 rows.
- `Transactor.platformTransaction(reason) { ... }` is the audited bypass for platform-admin work and for global tables. It's a separate database role with `BYPASSRLS`, used only by `/v1/admin/*` services, platform-wide jobs and the sign-in steps that run before a restaurant is known. Each use writes `reason` to the debug log; admin operations are audited anyway.
- Repository methods on tenant tables take a `RestaurantId` and filter by it as well (two controls).
- Every transaction sets `statement_timeout` from config (5 s; reports 10 s; architecture §10).

## 8. Staff and admin sign-in
This section turns architecture §7 into endpoints. The numbers (Argon2id parameters, lifetimes, lock rules) come from there and from S-4. They're not repeated with their reasons.

### 8.1 Sign-in: `POST /v1/auth/sign-in`
Body `{"email", "password"}`.
1. Per-IP rate limit (§11).
2. Normalise the email (trim, lower-case with `Locale.ROOT`) and look up `staff_accounts` by it.
3. Take one of the 4 Argon2id slots (wait at most 2 s, else `503 service_busy`). Verify the password against the account's hash, or against a fixed dummy hash when there's no usable account, so every path costs the same time.
4. **Failure** (no account, `status` not `active`, `locked_until` in the future, or a wrong password): one atomic `UPDATE` on an existing, unlocked account:
   - if the 15-min window has expired, reset the count to 1 and start a new window; otherwise add 1;
   - at 10, set `locked_until = now() + 15 min`.

   Tries while the account is locked aren't counted, so the lock can't be extended without end. Write the audit event in the same transaction. Answer `401 invalid_credentials`.
5. **Success:** reset the counter. If the stored hash uses older Argon2id parameters, re-hash and save it. Then:
   - platform admin → create a single-use MFA challenge (5 min) and answer `200 {"mfa_required": true, "mfa_token": "...", "expires_in": 300}`;
   - staff → create a session and its first refresh token (§8.3) and answer `200` with the token response and the refresh cookie.

Token response:
```json
{ "mfa_required": false, "access_token": "eyJ...", "token_type": "Bearer", "expires_in": 900, "audience": "staff" }
```

### 8.2 MFA step: `POST /v1/auth/mfa`
Body `{"mfa_token", "code"}`.
- Consume the challenge (`UPDATE ... SET used_at = now() WHERE token_hash = ? AND used_at IS NULL AND expires_at > now()`). Not found → `401 invalid_credentials`.
- Check the TOTP code (RFC 6238, ±1 step). The matched step must be greater than `totp_last_step`; save it in the same `UPDATE`, so a code can't be used twice.
- A wrong code counts towards the same lock as a wrong password, and the challenge is used up; the admin signs in again.
- Success → a session with `amr = ["pwd","otp"]`, `audience = admin`, and the token response with `"audience": "admin"`.

### 8.3 Sessions and refresh: `POST /v1/auth/refresh`
**In plain words:** the access token lives 15 min, so the staff app needs a way to get a new one without asking for the password again. That's the refresh token, kept in a cookie that page scripts can't read. Each use swaps it for a new one. If an old one ever comes back, someone has copied it, so the whole sign-in is ended.

- A **staff session** is one sign-in: its ID is the `sid` claim. It ends 24 h after sign-in (`expires_at`), on sign-out, or when it's revoked.
- A **refresh token** is 256 random bits, stored as a SHA-256 hash. It's valid until `min(issued_at + 12 h, session.expires_at)` and can be used once.
- Body `{"audience": "staff" | "admin"}`; the token comes from the cookie for that audience.
- The refresh is one atomic step: `UPDATE staff_refresh_tokens SET used_at = now() WHERE token_hash = ? AND used_at IS NULL AND idle_expires_at > now() RETURNING session_id`, and the session must be live. Then a new token is inserted for the same session, a new access token is signed, and the cookie is replaced.
- **Reuse:** if the hash exists but `used_at` is set, revoke the session (`revoke_reason = 'refresh_reuse'`), audit it, clear the cookie and answer 401.
- Any other failure → 401 with the cookie cleared.
- A refresh doesn't run Argon2id and isn't audited (≈ 6/s at 5,000 staff), but it is rate limited per IP.

**Cookie** (architecture §7):
- name `__Secure-rt-staff` or `__Secure-rt-admin` (one per audience, so a staff sign-in and an admin sign-in in the same browser don't overwrite each other);
- `HttpOnly; Secure; SameSite=Strict; Path=<auth cookie path>`, where the path is `/api/v1/auth`: the staff and admin web apps reach the API through a same-origin rewrite (`/api/*` → the API) in every environment (owner, 2026-10-15), so the cookie belongs to the app's own address and works on `*.vercel.app` without a custom domain;
- `Max-Age` equal to the token's remaining validity.

All `/v1/auth/*` `POST`s need `Content-Type: application/json`. A cross-site form can't send that without a CORS preflight, which the allow-list refuses. With `SameSite=Strict` that covers CSRF.

**Two tabs.** If two tabs of the staff app refresh with the same token at once, the second looks like reuse and ends the session. The staff and admin apps serialise refreshes across tabs (the Web Locks API or a `BroadcastChannel`), and the server keeps the strict reuse rule with no grace period (owner, 2026-10-15). This is a requirement on the web apps.

### 8.4 Sign-out: `POST /v1/auth/sign-out`
Body `{"audience"}`, plus the cookie, plus the access token when the app still has one. Revoke the session found by either, clear the cookie, audit, and answer `204`. Answer 204 even when nothing matched, so the app can always sign out cleanly.

### 8.5 Invitations and password resets
The links are issued in the `restaurants` design. Here they're used:
- **`POST /v1/auth/links/inspect`** `{"token"}` → `200 {"kind": "invitation" | "password_reset", "email", "display_name", "restaurant_name"?, "role"?, "totp_enrolment_required"}`. It lets the page greet the person before they choose a password, and changes nothing. A bad token → `404 link_invalid`. It's a POST so the token never appears in a URL.
- **`POST /v1/auth/invitations/accept`** `{"token", "password", "totp_code"?}`:
  - **Staff:** check the password rules (§8.6), store the hash, set `status = active`, use up the link, audit → `204`. The app then signs in normally.
  - **Platform admin, first call (no `totp_code`):** check the password rules, generate a TOTP secret, store it encrypted as `totp_pending_secret` (replacing any earlier one), and answer `200 {"totp_setup": {"secret": "<base32>", "otpauth_uri": "otpauth://totp/..."}}`. The link isn't used up yet, so a person who closes the page can start again.
  - **Platform admin, second call** (same token, same password, plus `totp_code`): verify the code against the pending secret, then store the password hash, move the pending secret to `totp_secret`, save the step, activate, use up the link, audit → `204`. A wrong code → `400 validation_failed` on `/totp_code`, and the link stays valid.
- **`POST /v1/auth/password-resets/complete`** `{"token", "password"}`: check the rules, store the new hash, clear the lock counters, **revoke all of the person's sessions**, use up the link, audit → `204`. An admin's TOTP secret is kept: a lost authenticator is a separate reset (`restaurants` design).
- Each of these is rate limited per IP. A link stays valid until it's used, replaced or expires (72 h invitation, 24 h reset).

### 8.6 Password rules (ASVS 5.0 V6.2)
- 8 to 64 characters, counted as Unicode code points after NFC normalisation. Any character is allowed, spaces included. No composition rules and no truncation.
- Rejected if it's on the bundled common-password list (the 100,000 most common, from a public list such as SecLists; the file ships in the JAR), or if it equals the email or the part before `@` (case-insensitive).
- A rejection → `400 password_rejected` with `errors[0].code` one of `too_short`, `too_long`, `too_common`, `matches_email`.

### 8.7 Change password: `POST /v1/auth/password`
Staff or admin access token. Body `{"current_password", "new_password"}`.
- Verify the current password (same Argon2id slot and lock counter as sign-in). Wrong → `401 invalid_credentials`.
- Check the rules, store the new hash, **revoke all of the person's sessions including this one**, clear the cookie, audit → `204`. The app signs in again.
- Admins aren't asked for a TOTP code here: their token already carries `otp`.

### 8.8 Who am I: `GET /v1/auth/me`
Staff or admin access token → `200 {"staff_id", "email", "display_name", "role"?, "restaurant": {"id", "name"}?, "platform_admin", "amr", "session_expires_at"}`. The staff app uses it after sign-in and refresh to decide which screens to show. The server still checks every call.

## 9. Data model
**Change from architecture §4, accepted by the owner on 2026-10-15 (§16 Q1):** sign-in has to find an account by email **before** the restaurant is known, and platform admins belong to no restaurant. So the account data is a **global table, `staff_accounts`, without RLS**. It replaces the `staff_members` table that §4 lists under `restaurants` (§4 leaves table names to Phase 3). Isolation for it rests on the repository: every query that a restaurant's staff can trigger filters by `restaurant_id`, and the matrix tests check it. The `restaurants` design manages staff through these tables via a `StaffAccounts` port that `core` provides.

```sql
-- core/auth: global (no RLS); one row per staff member or platform admin
CREATE TABLE staff_accounts (
  id                    uuid PRIMARY KEY,                   -- UUID v7
  email                 text NOT NULL,                      -- trimmed, lower-cased, ≤ 254
  display_name          text NOT NULL CHECK (char_length(display_name) BETWEEN 1 AND 100),
  phone                 text,                               -- optional (requirements §5)
  restaurant_id         uuid REFERENCES restaurants (id),   -- NULL only for platform admins
  role                  text CHECK (role IN ('manager', 'waiter', 'kitchen')),
  is_platform_admin     boolean NOT NULL DEFAULT false,
  status                text NOT NULL CHECK (status IN ('invited', 'active', 'deactivated')),
  password_hash         text,                               -- PHC string; NULL until the invitation is accepted
  password_changed_at   timestamptz,
  totp_secret           bytea,                              -- AES-256-GCM: key id ‖ nonce ‖ ciphertext ‖ tag
  totp_pending_secret   bytea,                              -- during enrolment only
  totp_last_step        bigint,
  failed_count          integer NOT NULL DEFAULT 0,
  failed_window_start   timestamptz,
  locked_until          timestamptz,
  created_at            timestamptz NOT NULL,
  updated_at            timestamptz NOT NULL,
  deactivated_at        timestamptz,
  anonymised_at         timestamptz,                        -- retention: 30 days after deactivation
  version               integer NOT NULL DEFAULT 0,
  CHECK ((is_platform_admin AND restaurant_id IS NULL AND role IS NULL)
      OR (NOT is_platform_admin AND restaurant_id IS NOT NULL AND role IS NOT NULL))
);
CREATE UNIQUE INDEX staff_accounts_email_uq ON staff_accounts (email);
CREATE INDEX staff_accounts_restaurant_ix ON staff_accounts (restaurant_id, status);

-- one row per sign-in; id = the token's sid
CREATE TABLE staff_sessions (
  id             uuid PRIMARY KEY,
  staff_id       uuid NOT NULL REFERENCES staff_accounts (id),
  audience       text NOT NULL CHECK (audience IN ('staff', 'admin')),
  amr            text[] NOT NULL,
  started_at     timestamptz NOT NULL,
  expires_at     timestamptz NOT NULL,                      -- started_at + 24 h
  revoked_at     timestamptz,
  revoke_reason  text CHECK (revoke_reason IN ('sign_out', 'refresh_reuse', 'password_changed',
                                               'password_reset', 'role_changed', 'deactivated'))
);
CREATE INDEX staff_sessions_live_ix ON staff_sessions (staff_id) WHERE revoked_at IS NULL;

CREATE TABLE staff_refresh_tokens (
  token_hash       bytea PRIMARY KEY,                       -- SHA-256 of the 256-bit token
  session_id       uuid NOT NULL REFERENCES staff_sessions (id) ON DELETE CASCADE,
  issued_at        timestamptz NOT NULL,
  idle_expires_at  timestamptz NOT NULL,                    -- min(issued_at + 12 h, session expires_at)
  used_at          timestamptz
);

CREATE TABLE staff_mfa_challenges (
  token_hash  bytea PRIMARY KEY,
  staff_id    uuid NOT NULL REFERENCES staff_accounts (id),
  expires_at  timestamptz NOT NULL,                         -- + 5 min
  used_at     timestamptz
);

CREATE TABLE staff_link_tokens (
  token_hash     bytea PRIMARY KEY,
  staff_id       uuid NOT NULL REFERENCES staff_accounts (id),
  kind           text NOT NULL CHECK (kind IN ('invitation', 'password_reset')),
  created_by     uuid NOT NULL REFERENCES staff_accounts (id),
  created_at     timestamptz NOT NULL,
  expires_at     timestamptz NOT NULL,                      -- + 72 h / + 24 h
  used_at        timestamptz,
  superseded_at  timestamptz                                -- set when a newer link is issued
);
CREATE INDEX staff_link_tokens_staff_ix ON staff_link_tokens (staff_id, kind) WHERE used_at IS NULL AND superseded_at IS NULL;

-- core: tenant table, RLS forced (policy on restaurant_id); NULL = platform-admin operation, written by the bypass role
CREATE TABLE idempotency_keys (
  scope            text NOT NULL,                           -- guest:<device> | staff:<id> | admin:<id>
  operation        text NOT NULL,                           -- route template
  key              text NOT NULL,
  restaurant_id    uuid,
  request_hash     bytea NOT NULL,
  response_status  integer,                                 -- set before commit, so never NULL once committed
  response_headers jsonb,
  response_body    bytea,
  created_at       timestamptz NOT NULL,
  PRIMARY KEY (scope, operation, key)
);
CREATE INDEX idempotency_keys_created_ix ON idempotency_keys (created_at);
```

The audit tables are in §12.

**Indexes for the hot paths:**
- sign-in: `staff_accounts_email_uq`;
- every staff call: the primary keys of `staff_accounts` and `staff_sessions`;
- refresh: the primary key of `staff_refresh_tokens`.

**Cleanup**, added to the hourly purge job (architecture §10), not a new cron: delete refresh tokens and MFA challenges expired more than 1 day ago, sessions ended more than 30 days ago, and links expired more than 30 days ago. Anonymising deactivated accounts after 30 days is part of the daily retention job: email → `deleted+<id>@invalid`, name → `Deleted user`, phone → NULL, password and TOTP secrets → NULL. The ID stays, so the audit log still points to it.

## 10. Endpoints
| Method and path | Auth | Idempotency | Success | Errors |
|---|---|---|---|---|
| `POST /v1/auth/sign-in` | None | — | 200 token response or `mfa_required` | 400, 401 `invalid_credentials`, 429, 503 `service_busy` |
| `POST /v1/auth/mfa` | None (MFA token in body) | — | 200 token response | 400, 401, 429 |
| `POST /v1/auth/refresh` | Refresh cookie | — | 200 token response + new cookie | 400, 401, 429 |
| `POST /v1/auth/sign-out` | Cookie and/or access token | — | 204 | 429 |
| `POST /v1/auth/links/inspect` | None (link token in body) | — | 200 link details | 400, 404 `link_invalid`, 429 |
| `POST /v1/auth/invitations/accept` | None (link token in body) | — | 204, or 200 `totp_setup` | 400 `password_rejected` / `validation_failed`, 404 `link_invalid`, 429 |
| `POST /v1/auth/password-resets/complete` | None (link token in body) | — | 204 | 400 `password_rejected`, 404 `link_invalid`, 429 |
| `POST /v1/auth/password` | Staff or admin token | — | 204 | 400 `password_rejected`, 401, 429 |
| `GET /v1/auth/me` | Staff or admin token | — | 200 | 401 |

The auth routes don't take an `Idempotency-Key`. A retried sign-in just signs in again, and the replay rules for the token endpoints would be worse than a second session.

**Suspension** (restaurants §6): every `/v1/auth/*` route is `allowedWhenSuspended`. None shows restaurant data, and a suspended restaurant's staff must still be able to change a password or finish a reset (owner, 2026-10-15, G3 pass Q-9). The admin routes are too, because an admin has no restaurant of their own and must be able to reactivate one.

**Scheduled jobs.** Every `/internal/jobs/*` route, in one place. Vercel Cron calls each with the cron secret; each is idempotent, works in bounded batches and holds `pg_try_advisory_xact_lock` (architecture §10). On the free Hobby account every job runs once a day (realtime §10).

| Route | On Pro | Work | Design |
|---|---|---|---|
| `/internal/jobs/outbox-sweep` | Every minute | Publish outbox rows the requests didn't | realtime §4.3 |
| `/internal/jobs/event-purge` | Hourly | Delete events and sent outbox rows older than 7 days | realtime §10 |
| `/internal/jobs/purge` | Hourly | Idempotency keys older than 24 h; expired refresh tokens, MFA challenges and links | §4, §9 |
| `/internal/jobs/session-auto-close` | Hourly | Close empty sessions idle for 2 h | tables §3.5 |
| `/internal/jobs/sales-reconcile` | Hourly (each restaurant after its local 03:00) | Rebuild the last 2 days of the daily aggregates | reports §5 |
| `/internal/jobs/retention` | Daily | Clear item and reason notes 30 days after close; delete replaced and deleted menu images after 30 days; anonymise staff 30 days after deactivation; archive orders and bills older than 2 years | orders §6, menu §6, §9, architecture §6 |
| `/internal/jobs/audit-export` | Daily | Export the previous day's audit entries to locked object storage | §12 |

## 11. Rate limits
A `RateLimiter` port; the adapter is Upstash with fixed windows (ADR-0008). Key `rl:<policy>:<subject>:<window start>`. Past the limit → `429 rate_limited` with `Retry-After` set to the window's remaining seconds. If Redis fails, the limit fails open and the WAF still applies. The connection opens at startup (S-1 Q10 design rule).

**Limits for this design**, accepted by the owner on 2026-10-15 as starting values (configurable; §16 Q3). The other features add their own (ASSUMPTION-4).

| Policy | Subject | Limit | Why this size |
|---|---|---|---|
| `auth.sign_in` | IP | 30 / 1 min | A restaurant's staff share one IP; 30 covers a large shift change |
| `auth.mfa` | IP | 10 / 1 min | Fewer than 10 admins |
| `auth.refresh` | IP | 120 / 1 min | 20 devices per restaurant refresh about every 15 min; leaves room for reloads |
| `auth.link` | IP | 10 / 1 min | Inspect, accept and reset together |
| `auth.password_change` | Staff ID | 5 / 15 min | Rare |
| WAF backstop on `/v1/auth/*` | IP | 300 / 1 min | Above every app limit, so only floods reach it |

The per-account lock (§8.1) lives in PostgreSQL and works even when Redis is down.

## 12. Audit log
NFR-SEC-03 and architecture §11. `AuditLog.record(event)` is called inside the transaction of the change it records, so there's never a change without its entry, or an entry without its change.

```sql
-- tenant table, RLS forced on restaurant_id; NULL = the platform chain, written by the bypass role
CREATE TABLE audit_events (
  id            uuid PRIMARY KEY,                           -- UUID v7
  restaurant_id uuid,
  chain_seq     bigint NOT NULL,
  occurred_at   timestamptz NOT NULL,
  actor_type    text NOT NULL CHECK (actor_type IN ('staff', 'admin', 'guest', 'system', 'anonymous')),
  actor_id      uuid,
  action        text NOT NULL,                              -- e.g. auth.sign_in.failed
  target_type   text,
  target_id     uuid,
  request_id    text,
  ip            inet,
  user_agent    text,                                       -- first 200 characters
  details       jsonb NOT NULL DEFAULT '{}',                -- no secrets, passwords, tokens or free text
  prev_hash     bytea NOT NULL,
  hash          bytea NOT NULL,
  UNIQUE NULLS NOT DISTINCT (restaurant_id, chain_seq)
);
CREATE TABLE audit_chain_heads (
  chain_key  uuid PRIMARY KEY,                              -- restaurant ID, or the nil UUID for the platform chain
  last_seq   bigint NOT NULL,
  last_hash  bytea NOT NULL
);
```

- **Hash chain**, one per restaurant plus one for the platform. Appending: `SELECT ... FROM audit_chain_heads WHERE chain_key = ? FOR UPDATE`, then `hash = SHA-256(prev_hash ‖ JCS(row without the hashes))` (RFC 8785 canonical JSON), insert, update the head. If a row is changed or removed, every later hash stops matching. Audited actions are infrequent per restaurant, so the head lock doesn't slow anything that matters.
- **Grants:** the `app` role has `INSERT` and `SELECT` on `audit_events`, and no `UPDATE` or `DELETE` (a test checks it). Deleting entries past retention (1 year, TBD-4) is a `SECURITY DEFINER` function that may only remove a whole oldest prefix of a chain, and it records where the remaining chain now starts. The design is finished in Phase 4.
- **IP:** from Vercel's `x-real-ip` (set by the edge, not by the client).
- **Nightly export** to object storage with a retention lock (architecture §11). The provider depends on TBD-10; the job is designed with the `reports` and operations work.

**Auth actions.** Failed sign-ins are recorded against the account's restaurant when the account exists. Otherwise they go to the platform chain with an HMAC of the typed email, so repeated tries can be correlated without storing what was typed.

| `action` | When | `details` |
|---|---|---|
| `auth.sign_in.succeeded` | §8.1 success (staff), or §8.2 (admin) | `amr` |
| `auth.sign_in.failed` | §8.1 failure | `reason`: `unknown_email`, `bad_password`, `locked`, `inactive`; `email_hmac` when unknown |
| `auth.account.locked` | The 10th failure | `until` |
| `auth.mfa.failed` | Wrong or reused TOTP code | — |
| `auth.refresh.reuse_detected` | §8.3 reuse | `session_id` |
| `auth.sign_out` | §8.4 | `session_id` |
| `auth.password.changed` | §8.7 | — |
| `auth.password_reset.completed` | §8.5 | — |
| `auth.invitation.accepted` | §8.5 | `role` |
| `auth.totp.enrolled` | §8.5, admin | — |

The `restaurants` design adds `staff.invited`, `staff.role_changed`, `staff.deactivated`, `staff.password_reset_issued` and `admin.totp_reset`.

## 14. Code layout
One Gradle module, packages by feature (ADR-0001). `<base>` is the root package chosen at Phase 4 start.

```
<base>.core
  domain/        Ids (RestaurantId, StaffId, ...), Money, DomainError, Clock
  application/   Caller, StaffRole, Transactor, IdempotencyStore, AuditLog, RateLimiter (ports)
  persistence/   ExposedTransactor (tenant + platform), IdempotencyRepository, AuditRepository
  http/          ProblemDetails (StatusPages), RequestId, ClientVersion, Idempotent { } route helper,
                 ETag / If-Match helpers, Pagination, CORS and headers setup
  auth/
    domain/      StaffAccount, StaffSession, PasswordPolicy, LockoutPolicy
    application/ SignInService, MfaService, RefreshService, LinkService, PasswordService, StaffAccounts (port for restaurants)
    persistence/ StaffAccountRepository, StaffSessionRepository, LinkTokenRepository

```

`core/http/Endpoints.kt` is the one place every endpoint is declared (§16), for example `Endpoints.Auth.SIGN_IN`. Each entry holds the method, the path, the route group, whether it needs an `Idempotency-Key` or `If-Match`, and `allowedWhenSuspended` (restaurants §6), which has no default. Route files and the authentication providers read it.

The crypto classes are ported from `spikes/s4-auth`, where they passed 19 of 19 token cases. They get rewritten with tests rather than copied, because spike code is throwaway.

## 16. Owner decisions (2026-10-15)
The owner accepted all five recommendations. They're recorded in STATUS.md (Decisions; Q-2 resolved).

1. **Global `staff_accounts` table without RLS** (§9). Isolation for it is the repository's `restaurant_id` filter, checked by IT-CORE-07. No CR: architecture §4 leaves table names to Phase 3. Rejected alternative: `SECURITY DEFINER` lookups.
2. **Same-origin rewrite** for the staff and admin web apps (`/api/*` → the API) in every environment; refresh cookie path `/api/v1/auth` (§8.3, §13). No custom domain is needed.
3. **Rate limits in §11** as starting values.
4. **Strict refresh-token reuse rule**; the web apps serialise refreshes across tabs (§8.3). Rejected alternative: a server grace period.
5. **ASSUMPTION-5 confirmed:** staff and admin access tokens live 15 min.

**Also decided: one central endpoint registry** (owner, 2026-10-15). Every endpoint is declared in one place in the code, `core/http/Endpoints.kt`, as the path constants per route group. Feature route files use those constants, never string literals. A test compares the registered Ktor routes with both the registry and `docs/api/openapi.yaml`, and fails on any difference (architecture §12, API9). The rule is in CLAUDE.md.
