# ADR-0006: Signed QR tokens and table-session tokens for anonymous guests

| Status | Date | Deciders | Requirements |
|---|---|---|---|
| Accepted | 2026-10-13 | Manh Nguyen (tech lead) | FR-001, FR-031, FR-013, NFR-SEC-02, NFR-SEC-04 |

## Context
Guests have no accounts. The QR code is the only proof of being at a table (ASSUMPTION-6). Codes must be rotatable, unguessable and usable by both the mobile app and the web app. Closing a session must cut off its guests at once.

## Options
1. **Random opaque QR token stored hashed in the database; opaque session token stored in the database**
   - Pros: simple revocation.
   - Cons: a database lookup for every token.
2. **Signed QR token (restaurant, table, key version, `kid`) + short-lived signed session JWT, with an "is the session open" check in the database on every guest call**
   - Pros: forged codes are rejected without a database hit; rotation by key version; immediate revocation through the session check, which the guest calls make anyway.
   - Cons: we must manage signing keys.
3. **Guest tokens from the staff IdP** (anonymous users)
   - Pros: one token system.
   - Cons: couples guest traffic to the IdP's limits and costs.

## Decision
Option 2:
- ES256 keys with `kid`, held in Vercel sensitive environment variables and rotated with overlap.
- The QR URL is `https://<app-domain>/t/<qrToken>`, which opens the app through App Links / Universal Links and the web app otherwise.
- Session JWT lifetime is 6 h; `sub` is a random device ID generated by the client app.

## Consequences
- Positive: no IdP dependency for guests; abuse is limited by rotation and rate limits.
- Negative: a photographed code works until it is rotated (R-02); FR-016 waiter confirmation is the stronger control if needed (TBD-8).
- Follow-ups: Phase 3 defines the token formats, the claims and the rotation runbook.
- Note (2026-10-14, CR-002): staff and admin tokens are also issued by the service (ADR-0011) with the same ES256 mechanism, but with their own signing keys and audiences (`staff`, `admin`), so a guest key can never verify a staff token. Option 3 no longer applies: there is no external IdP.
